本轮重新核对源码、真实工程配置、数据契约与全部用户入口，执行原生回归和新增边界探针。没有用旧截图替代本轮结果，也没有将领域层方法算作用户已经可用的界面。本报告不表示已修复全部问题、已完成真机验收、已上传或已通过商店审核。

## 架构和设计判断

当前是原生 SwiftUI + 必要 UIKit 分类拖动组件，导航、列表、表单与系统文件面板符合 iOS 使用习惯。用户确认的中央记账动作、iCost 式时间栏、两级分类两行展示、统计同页下钻继续保留，不做无依据的重新设计。

领域、状态提交、仓储分层已经建立，整数分、稳定 ID、统一校验、先写入后通知以及失败回滚值得保留。主要风险在跨页面口径与呈现边界：同一个余额应使用同一个截至日期，主题应传到每个 sheet 根，长文本要在组件层处理，文档要区分后端方法与 UI 入口。此时不需要重写架构或引入服务端。

| 原生审查维度 | 暂定分 / 4 | 证据与限制 |
|---|---|---|
| 无障碍 | 2 | 有标签和大字号路径；仍有普通文案固定字号，VoiceOver 未听读 |

## 从内测到上架的下一批工作

1. **正确性和核心任务**：先关闭 R01、R09，补负向和跨页面断言；保持失败用例可复现。
2. **全页一致性**：统一退款/转账/日期/分类弹层主题，改普通文案字号适配，检查空、错、退出、长文本与键盘。按本轮图集逐项签收。
3. **产品发布收口**：图标、中文资源声明、清理开发占位/测试资源、政策与支持页面，最终商店截图和描述。
4. **设备和数据生命周期**：真实 Files 备份→选择→恢复、旧版覆盖安装、离线、后台、锁屏、跨日、VoiceOver 和性能；不能用再次跑正常首页代替。
5. **分发闭环**：确认团队/范围/地区/定价与支持身份，签名归档→Validate→TestFlight→设备回收→提交审核；审核通过后再决定发布。

界面修复可依次使用 `/impeccable harden`（长名称）、`/impeccable colorize`（弹层主题）、`/impeccable adapt`（字号）和 `/impeccable polish`（最终一致性）。修复后重跑审查；这些检查应由开发流程主动完成，不把审美和动线把关全部留给用户。
