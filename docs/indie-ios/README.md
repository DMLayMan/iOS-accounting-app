# 独立 iOS 应用：从余记提炼的设计与交付方法

沉淀日期：2026-09-11。来源是本 session 的用户反馈、当前实现、设计记录和原生验收。目标是让下一款记账、待办、日程或其他个人工具更快做对，而不是把余记复制一遍。

**最值得带走的经验：先做少而完整的用户任务，再扩大功能；把人的输入、上下文和数据保护好；用原生证据结束争论；让每次已确认的设计留下可复用的契约。**

## 先读这八条

1. **效率首先来自少返工。** 本次时间控件多轮更换仍被否定，根因是先换控件，后理解任务和视觉层级。下一次先写清“相邻浏览”和“远期检索”等具体问题，再选形态。
2. **美感从信息结构开始。** 分类/标签重叠、重复入口、无意义的固定占位，靠配色修不好。先减概念和打断，再精修间距、字号、材质与颜色。
3. **界面服务任务，不能让用户管理实现。** 快捷项、搜索、管理可以是同一集合的不同入口；用户不应理解两套其实相同的分类体系。
4. **操作连续性比某个控件更重要。** 图表到明细、就地新增分类、记账后返回原页，价值在于保留上下文。不是所有问题都需要跳页或七分屏。
5. **情绪价值先做确定感。** 不丢输入、可撤销、错误有解释、下次能继续，比多一段庆祝动画更能建立长期信任。
6. **复用要包含行为和状态。** 流水/统计共用颜色仍可能各有一套时间逻辑；完整组件契约和唯一状态来源才能避免后续分叉。
7. **本地应用也有高风险工程问题。** 读失败覆盖原文件、退款断链、草稿误清，都会直接伤害使用体验。数据恢复和兼容是产品能力，不是发布前补丁。
8. **Agent 自己把关，用户决定取舍。** 用户不应该承担发现键盘叠层、取消弹窗难看、图表跳转割裂的工作。先完成有依据的原生走查，再把真正的偏好取舍交给用户。

这些是工作方法和本次观察。没有真实用户长期使用数据，不宣称已量化节省多少时间或达到“极致体验”。

## 下一款 App 从这里开始

### 第一步：确认一条最常用的任务

例如待办：“想起一件事时立刻记下，并在今天需要时找到它。”先确定首次打开的位置、默认归属、最少输入和完成反馈。不要一开始就要求设置项目、标签、优先级、周期、提醒、主题。

领域先明确：项目是否是单归属，标签是否确有跨项目用途；重复任务、截止时间、提醒时间是否不同。余记的一笔一个二级分类不能替代这里的产品判断。

### 第二步：把中断与纠错一起画出来

新建时离开、编辑后放弃、完成后撤销、写入失败、重启恢复，各自怎样处理？从今天列表新增后回到今天，从搜索结果打开详情后返回仍能找到原位置。空状态应能直接开始第一条任务。

### 第三步：尽早运行一个原生切片

实现创建 → 保存 → 回读 → 编辑/取消 → 错误恢复，再扩展检索或统计。键盘、拖动、时间选择、sheet 高度尽早在普通屏和小屏看；静态原型只验证它实际能证明的部分。

### 第四步：按风险增加能力

用户开始真实使用后，查“哪一步重复、哪个状态难找、哪种错误难恢复”。高频阻力和低频高损失优先。高级组织方式、复杂统计、主题和云共享按需求递进，不把已列出的能力全部作为首版必选。

### 第五步：固定当前设计与交付事实

每次实现同时维护当前 PRD、页面契约、必要的架构变化和对应证据。已否定方案进历史记录；产品画面只有一个当前版本。测试和审美走查按变更收敛，避免全量反复重跑却没有新信息。

## 如何让 Agent 使用

本机发现路径为 `~/.codex/skills/indie-ios-product/`，仓库里的 `skills/indie-ios-product/` 是维护源。本次后续会话的可用技能列表已包含它，并已用于待办设计练习；这证明可发现和可读取，不等于自动匹配的长期可靠性已验证。若某个会话未刷新列表，可直接给出安装路径并要求读取。

可直接使用的请求：

```text
使用 $indie-ios-product，为一个本地优先的 iPhone 待办应用设计首个可交付切片。
先确定高频任务、概念和退出语义，给出原生动线；不要直接照搬记账的分类和 Tab。
关键选择有依据后，完成当前授权范围内的实现、适配检查和交付文档。
```

```text
使用 $indie-ios-product 审查当前新增页面。
重点检查键盘、取消/草稿、创建后回到哪里、小屏大字号，以及共享组件是否发生分叉。
按真实问题修复并验收，不重新设计已确认的产品结构。
```

这个 Skill 不取代已有视觉专项能力；它负责把产品、交互、工程和证据串起来，不要求安装其他工具、不授权远端操作、不修改所有项目的全局约定。

## 成功标准与后续维护

以后评估这份沉淀是否有用，看四件事：能否少走一次已知弯路；新用户能否独立完成核心任务；改动是否更少破坏其他页面；是否能清楚说明“验证到了哪里”。可记录任务时间、返工轮次、上下文跳转、失败恢复步骤和维护耗时，但区分设计目标、人工走查、真实使用测量。

这次 Skill 已做结构、引用和本机安装一致性校验，并做场景桌面推演；[验证记录](skill-validation.md)明确边界。**它尚未在第二款真实 App 上完成效果验证**，不要把本次测试通过等同于方法已得到普遍验证。

维护时先改仓库版本，验证后同步到本机发现路径；保持两份一致。新经验只有在改变后续决策时才加入规则；单个产品的布局保留在案例。新增一款 App 后，记录哪些规则帮助减少返工、哪些误导了设计，再修正 Skill，避免越沉淀越臃肿。

从仓库根目录可重复检查，命令只读，不会把变化自动批准成新基线：

```sh
node --test scripts/verify-ios-playbook.test.mjs
node scripts/verify-ios-playbook.mjs
node scripts/verify-ios-playbook.mjs --installed "$HOME/.codex/skills/indie-ios-product"
```

前两项也纳入 CI。检查覆盖文档内联链接、Skill 自包含性、文件清单与哈希；安装核对需显式提供本机路径，CI 不声称检查过本机。它不执行远程来源、Markdown 锚点或设计质量审查；Skill 元数据仍用官方 `quick_validate.py` 校验。修改 Skill 时，在审查改动后再更新清单并同步本机，不要为了让校验变绿覆盖其他人的本地改动。
