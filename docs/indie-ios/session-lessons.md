# 本 session 的 15 个可迁移案例

范围：用户在本次会话中的连续反馈、余记当前产品契约及 2026-09-11 回归记录。下表的“观察”来自本次记录；“迁移”是提炼出的建议，不是已在所有应用验证的结论。

## 产品与交互

| 案例 | 本次观察与根因 | 当前取舍 | 下一次如何避免 | 不应机械推广 |
| --- | --- | --- | --- | --- |
| 1. 两种标签让人困惑 | 快捷与手输入口看起来属于不同概念，用户不得不理解实现区别 | 明确一笔一个二级分类，备注仅记录 | 先做实体/基数/变更影响表；快捷选择、搜索、管理同一实体 | 不能推导所有 App 都不需要标签或备注搜索 |
| 2. 二级分类屏效低 | 为固定两行而分布稀疏，少量项也被拆行；缺少就地新增和灵活排序 | 少量一行、较多最多两行再横向浏览；长按挪位，区域内新增 | 用 1、3、8、超过一屏的真实数量检查阅读与动作 | 两行四列只是余记方案，不是目录通用栅格 |
| 3. 两个键盘叠在一起 | 数字输入与文本焦点没有统一模式 | 文本焦点时关闭金额键盘，确认退出也先处理键盘 | 将焦点、数字键盘、系统键盘、退出确认一起设计 | 不应据此禁止所有自定义键盘 |
| 4. 新建/编辑/取消太难看且语义混乱 | 用一个浮动确认处理不同保存语义，遮挡原内容，草稿容易互相影响 | 新建关闭留草稿；编辑就地继续/放弃；失败保留输入 | 先定义 dirty、草稿所有权与关闭状态机，再选容器 | 不要求每种新建都自动保存草稿 |
| 5. 下钻从跳页改七分屏仍被否定 | 只换容器，仍把分析对象带离上游图表 | 图表、分类、下游明细同页联动，单笔再进详情 | 区分过滤与浏览对象；设计明确的联动范围 | 不能禁止所有详情面板或层级页面 |
| 6. 账本页和流水页职责混淆 | 账本页重复列明细，流水缺少高效时间定位 | 账本看累计/余额，流水负责期间和组合检索 | 每个根入口只有一个可解释的主要任务 | 不要求所有 App 都有总览页 |
| 7. 时间控件反复改丑 | 三箭头、月份条、隐藏滑动、追加提示轮番出现；对顶部局部滑动的理解也偏离用户 | 按用户认可的 iCost 参考结构统一完整组件 | 在换控件前拆相邻浏览/跨年检索，核实竞品实际证据；定义手势区域 | 箭头不是原罪，iCost 结构不是唯一正确设计 |
| 8. 高频新增长期占整行 | 中心任务入口与内容密度没有一起考虑 | 五 Tab 中间记账适度突出，保存/取消回到发起页 | 比较入口触达、导航语义、固定占用和返回上下文 | 中央动作 Tab 不作为每款 App 的默认结构 |
| 9. 预算与更多规则会淹没主内容 | 0 到多条规则需要管理，但全部展开挤占分析和录入 | 管理处完整编辑；使用处相关提示、默认少量超额、可展开 | 管理完整性和使用时的信息优先级分开设计 | 低频高风险警告不能一律折叠隐藏 |
| 10. 色彩与主题不是最后刷一遍 | 收入支出原先缺乏差异；主题涉及根页、弹层、UIKit；真实回归发现弹层主按钮落回蓝色 | 主题、收支、图表颜色分工；主题色显式传递 | 先定义语义色，再检查所有承载表面和禁用/选中态 | 余记暖橙/青绿配色不直接套到医疗、日历等领域 |

## 工程与研发流程

| 案例 | 本次观察与根因 | 处理 | 下一次如何避免 | 验证边界 |
| --- | --- | --- | --- | --- |
| 11. 本地坏文件可能被空库覆盖 | 读失败被吞掉，继续允许写入；恢复和正常读写校验分叉 | 阻断写入、保留原路径、共同校验、恢复前保留副本 | 把损坏和恢复列入首个持久化切片；统一完整性边界 | 原子替换不证明断电和多进程安全 |
| 12. 生命周期和资源释放漏项 | 退款、回收站、草稿、最后账本关系有缺口；拖拽计时器持有 Coordinator | 保护引用与草稿，删除确认；销毁时主动停止刷新 | 审查创建之后的整个生命周期及持有关系，不只 CRUD 成功路径 | 500 条数据不证明所有数据规模/后台行为 |
| 13. 形式共用但语义分叉 | 两页时间 Tab 不统一，基础行/图标藏在某业务页 | 完整日期组件；共享行、图标、格式；分类/预算按领域拆分 | 写组件输入输出与状态所有权，列全调用方；不先造通用框架 | 只有意义相同的上下文才共享 |
| 14. 全量测试暴露测试工程问题 | 过时入口、键盘提交、固定日期与真实时钟冲突、小屏滑动落入固定栏；运行中修改脚本造成收尾错误 | 注入时钟、新 UUID 仓储、统一滚动区域、固定产物/脚本批次 | 领域先行、原生聚焦、共享变化扩大回归；先诊断失败层再修 | 原生 xcresult、运行器退出与最终场景覆盖分别证明 |
| 15. 文档落后会把旧设计带回来 | README 曾仍描述旧 Tab/悬浮入口，历史方案与最新规范并存 | 当前 PRD/UI/架构统一入口，历史标记，截图和哈希可分发 | 每次确认变更同步行为、状态和证据；文档能复刻而非只记进度 | 文档存在不证明另一个 Agent 已成功复刻 |

## 自我纠偏：不再把基础把关交给用户

本 session 中，多个基本问题由用户主动指出：两套分类概念、键盘叠层、下钻割裂、少量分类错排、默认页定位、同一时间控件分叉。这说明仅“响应反馈后改代码”不够。下一次在展示前，Agent 应按任务连续性、视觉层级、状态完整性、数据可信度四个维度主动审查。

不能把“按反馈快速出了多版”本身当作效率。已有方向反复失败时，应该暂停同类外观补丁，明确根因并缩小不确定性。也不能把用户一时建议的容器当永久需求：用户认可的是便捷分析，七分屏只是曾经尝试的方案；最终同页联动更符合已确认任务。

同时，审查要有边界。完成一次集中原生检查、修复实际问题、再确认，通常比几十次孤立微调有效；如果存在真实功能错误继续关闭，不用“效率”作为放过错误的理由。

## 2026-10-08 复审追加的工程经验

2026-10-08 再次全量复审补充（[修复与证据](../review-fix-2026-10-08/README.md)）：

| 可复用经验 | 本次具体问题与处理 | 下一应用的验收方式 |
| --- | --- | --- |
| 给“当前”明确业务时钟 | 账户页包含未来记录，账本页截至今天；统一当前余额入口，未来期初未生效 | 核对跨页面日期口径，测试未来数据、跨日和前台恢复 |
| 检查点比较最后保存的值 | 后台后撤回到初始表单，若只比较初始值会留下旧草稿；显式清除撤回检查点 | 测“编辑→后台→撤回→后台→重启”，不只一次中断恢复 |
| 共享组件验证真实宿主 | 系统 sheet 根重置主题、SwiftUI 键盘附件栏出现负尺寸警告；呈现根传主题，表单内完成栏 | 检查嵌套呈现、UIKit、输入焦点与父子表单；保存调用栈证据 |
| 焦点与输入结果一起验证 | 共用预算字段没有宿主焦点契约，清除按钮出现改变行高；宿主枚举焦点 + 稳定 44pt 输入区。iOS 27 元素级输入 API 误报焦点，实际键盘可输入正确字段 | 检查下一字段、子页返回、清除前后；键盘输入后立即断言字符归属与保存结果，先诊断测试层，移除猜测性手势 |
| 把极端条件组合起来 | 长账户名与最大字号同时出现；压缩名称、日期保留宽度，无障碍改纵排 | 在小屏同时使用长名称和最大字号，保留完整朗读/选择路径 |
| 资源管理也是产品能力 | 恢复前副本不断积累且不可管理；增加预览/导出/单项确认清理，规范化路径 | 测取消、删除最新副本、落盘失败以及当前库不受影响 |
| 用关系数据挑战复杂度 | 分类退款反查导致二次增长，预算每条规则重复扫描；索引统一失效、一次聚合 | 用退款/删除/归档扩展 5k/50k；注明设备、优化编译、冷/热测量 |
| 发布资源从真实产物核对 | Debug 隔离不等于 Release 无夹具；未配置图标、政策及语言声明 | 检查 archive 文件与 Info，再独立验证签名、升级、分发、审核 |
| 测试选择先验证真实用例 | Xcode 会忽略不存在的 only-testing 名称；运行入口增加源码名称校验 | 正例确认目标，负例必须非零退出；按用例身份去重，保留失败和后续修复批次 |

这些经验不意味着所有应用都需要 JSON、备份或键盘完成栏。应迁移其状态、数据和证据契约；领域机制重新判断。

## 迁移到待办和日程时要重新判断什么

### 可选云协作的新增经验（2026-10-08）

| 可复用约束 | 本次落地 | 下一应用的验收 |
| --- | --- | --- |
| 同步与备份分别定义 | 云内容只含选中账本；备份去云绑定，恢复为本地，避免无意回滚他人数据 | 独立检查云范围、离线缓存、外部备份和恢复权限，不把文件可读当同步成功 |
| 业务修改与待传状态一起保存 | 同一个原子文件持久缓存/共同祖先差异；响应丢失可幂等重试 | 断网、重启、云已成功但本机落盘失败，仍能恢复待传内容且不重复实体 |
| 账号改变是隔离边界 | 系统身份、容器、环境、zone/owner；启动先隐藏，旧回复检查 epoch | A 待传→切 B→旧回复到达→切回 A，核对展示及上传归属 |
| 共享数据身份不等于缓存身份 | 同一账本 ID 可在两个账号缓存中出现；可见数据声明所属账号，仅捕获该账号 | 同一设备 A/B 均参加同一本，分别留离线修改，切回后合并；不能只测新账号没有成员关系 |
| 恢复与重新上传需要独立身份 | 备份保留业务 ID 便于核对，但再次启云先检查同源；需确认新建重映射 ID 的副本 | 取消不写，确认后两边原数据保留，新云副本没有相同身份的第二个 zone |
| 同步替换不应改变用户位置 | 安装远端版本时保留当前账本选择；临时删除实体不是用户切换 | 至少两个账本，刷新当前账本后导航、筛选期间、当前记录与草稿不跳走；先看保存数据再归咎弹窗 |
| 不安全合并宁可明确冲突 | 同字段编辑、删除对修改、并发退款超额，保存独立本机副本再采用云端 | 多客户端真实关系数据；不能只测并发添加，更不能用手机时钟覆盖 |
| 生命周期动作串行化 | 同步和退出同一 busy 通道；退出先保存本地副本 | 退出时正同步、磁盘失败、网络失败；其他成员数据不删除 |
| 展示状态只有一个来源 | 首页/设置共用待同步、暂停、问题及只读文案 | 每种故障截屏，不能把有缓存等同已经同步 |
| 原生 UI 语义须核对 | 合并图标/文案 AX；Tab binding 内延后发布提示；小屏提示先滚动再断言 | 真实层级与保存结果定位产品/测试差异，保留红测，不靠延时或弱化断言 |
| 模拟与真实云分开交付 | Debug + UUID 双门控的假适配；默认云配置关闭，签名/真实双账号单独清单 | 不把模型或模拟器通过写成跨账号已可用；Production 再验证邀请与权限 |

逐账本 CKAsset 条件提交是余记首版的具体取舍，不是所有应用的推荐架构；关系原子性换来全量资产传输，需要真机数据规模验证后再选择分块或实体提交。

| 可带走 | 待办需要重做的判断 | 日程需要重做的判断 |
| --- | --- | --- |
| 少概念、核心路径短 | 项目、标签、优先级是否独立；快速添加默认归属 | 日历、事件、任务是否独立；创建时必要字段 |
| 时间导航有快慢两条路 | 今天/即将到来/逾期是否比月更重要 | 日/周/月浏览、跨日期直接跳转与时区 |
| 保存/取消/恢复统一思考 | 完成与撤销、重复任务实例、离线草稿 | 改单次/后续/整个系列、冲突、参与人更新 |
| 分析可下钻核对 | 完成数不等于生产力，取消和恢复如何算 | 时间分布分母、重叠事件、全天事件如何算 |
| 本地优先、依赖有边界 | 提醒权限拒绝、离线依然可用 | 系统日历权限、现有事件保护、外部账户限制 |
| 体验状态需要证据 | 长任务名、批量完成、列表挪位 | 密集日程、跨午夜、夏令时和重复规则 |

这些是下一产品的待决策点，当前仓库没有实现或验证上述待办/日程能力。

## 2026-10-15：真实分发包验收的边界

- TestFlight 安装验证使用无 AUT 路径的独立 runner。普通 UI 测试会安装 Debug App，能看到相同版本号也不能证明正在测分发包；同时回读 TestFlight 页面与实际 CloudKit 环境。
- StoreKit 商品目录币种、系统确认页币种、已核实收据币种分别记录。美元不直接代表某个具体 Storefront，设备中文不代表人民币；App/系统相同 USD 不属于当前价格不一致。禁止为了测试变绿硬编码价格或自动退出日常购买账号。
- 人工付款/取消后先 activate 观察结果，不立即 launch。launch 会终止 App，可能人为中断回调并保留未决状态；这个状态不能当作未付款证明，也不能据此自动重试。
- 同 Bundle 的 Development/Production 验收包在 Mac 上可能抢占共享链接路由。固定接收包实际路径/签名环境，区分“系统打开 App”“收到 metadata”“接受成功”“远端快照回读”“双方新增/冲突/权限”。失败时保留证据，不把指定邀请已生成写成共享验证通过。
- 共享后闪退先取 ips，再重新打开应用。本轮工具重启后的正常首页一度遮蔽了真实崩溃；两份栈最终指向 sheet 主题读取缺失的 AppState。业务依赖必须从呈现侧捕获、显式传给 portal 根，并保持同一个实例，不能用新建空状态来兜底。普通导航打开页面不覆盖外部 callback 和冷启动入口。
- 接受邀请前 shared zoneNotFound 不等于成员权限被撤销，更不能证明账本丢失。先拿实际 metadata、完成接受和双端回读，才进入权限与撤销验收；未通过的探测也要留档，禁止自动重建数据“修复”。
- 更新磁盘包后核对运行进程。旧进程可能继续加载原代码；重验外部回调前安全退出 QA 端、按精确路径启动，确认启动时间晚于二进制更新。先由 Agent 把接收端准备正确，再请用户重发。
- 控件 exists 不代表可以操作。分享面板与隔空投送可以遮住整棵底层 App 树；本次错误点击的 hit point 为 -1。先识别最上层系统面板，或在共享已完成、没有未保存表单和购买回调时专门冷启动验收；不能照搬到支付取消路径。
- 同步成功按方向和数据版本核对。本轮 A 写入、B 接受和新增都通过，但 A 后续网络失败仍只缓存旧版本；必须保留“1 笔旧缓存/2 笔远端”的边界，不能因两个账号都出现同一账本就宣称双向恢复通过。
- 审核截图保留构建、来源、合成数据范围、尺寸与哈希。上传成功后刷新回读；早期真实 CNY 图可以作为同组件审核 UI 材料，但不能冒充后来 TestFlight 的币种验收。
