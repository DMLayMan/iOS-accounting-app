# 迁移示例：待办的首个可交付设计

性质：使用 `indie-ios-product` 完成的一份具体设计练习。用于检查方法能否产出可实施的决定，不是第二款 App 的立项、原生实现、用户测试或竞品调研结论。

## 1. 功能简报

**任务：想起一件事时快速记下；需要时找到；完成后放心划掉。**

场景假设：个人 iPhone、离线可用、短任务为主。首先验证“捕捉 → 今天回看 → 完成/撤销”的闭环；用户是否更希望默认进入收集箱，留给真实使用验证。设计不要求预先设置目录或授予通知权限。

首个切片只包含创建、今天/全部查看、编辑、完成与撤销、本地保存和读取失败恢复。搜索与回收站作为完整个人使用前的后续能力；提醒、重复任务、项目、标签和云共享不为了填满页面而提前出现。

| 概念 | 本切片定义 | 为什么没有照搬余记 |
| --- | --- | --- |
| 任务 | 一个稳定 ID、一段必填标题、创建时间；完成状态与完成时间一致 | 不包含交易类型、金额、分类或财务符号 |
| 安排日期 | 可空的当地日历日期；表示打算哪天做 | 不等同于硬截止时间或通知时间 |
| 今天/全部 | 同一任务集合的视图；不是两个任务存储位置 | 改安排日期不会复制任务 |
| 完成 | 完成标识与完成时间一起写入，撤销恢复原未完成状态 | 不能借用退款抵扣公式 |
| 项目与标签 | 此切片不开放；未来分别按归属与跨项目检索价值决定 | 不因余记合并标签而禁止待办标签 |

一个无日期任务仍可保存，并在全部列表的“未安排”组可见。今天模式只展示安排日为今天且未完成的任务；过去安排的未完成任务放在明确的“之前安排”组，避免偷偷消失。未来日期不出现在今天，但保存反馈说明“已安排到 9 月 15 日，可在全部查看”，不强行跳页。

## 2. 页面契约

只有一个主导航容器。标题“待办”；下方“今天 / 全部”选择视图；内容为任务列表；底部工具栏有“＋ 添加任务”，设置入口在标题区。两种视图都保留新增入口；键盘弹出时由原生编辑容器承载，不另造数字键盘。

这是单列表工具，中央动作 Tab 没有必要。后续若形成多个独立高频任务，再评估根导航，不能先为了和余记相似凑够五个 Tab。

```text
待办                                      设置
今天 | 全部

之前安排                              1 项
○ 预约洗牙                       9 月 10 日

今天                                  2 项
○ 给花浇水
○ 整理下周材料

[今日已完成 3 项 · 展开]

＋ 添加任务
```

以上为结构线框，不证明真实原生视觉。标题、任务文字与日期使用系统语义字号；任务内容是主层级，分组与数量次之。只用一种强调色表达操作，完成状态同时有形状/文字；“之前安排”不默认用警告红色指责用户。

## 3. 快速添加与编辑

新建是单一系统 sheet，打开直接聚焦标题，必填只有标题；安排日期一行可选，默认随来处：今天视图默认今天，全部视图默认未安排。标题区明确显示当前安排日期，避免隐形默认值。编辑完整任务沿用同一表单字段，不出现另一套快捷命名。

键盘提交键与显式“添加”执行同一命令；空白标题禁用并避免生成空任务。保存成功后返回原视图；若对象不符合当前视图条件，通过轻提示说明位置而不是偷偷改变筛选。列表定位新项，正常情况下不再增加成功弹窗。

为了完整定义中断，首个切片采用一份本地新建草稿，键为新建任务入口而不是今天/全部。重新打开先续写既有草稿并显示其日期，不用新的入口默认值覆盖它。编辑旧任务使用临时表单，不占用或清除新建草稿。

| 事件 | 行为与持久化边界 |
| --- | --- |
| 未输入就关闭 | 直接关闭，不写空草稿 |
| 新建有内容时关闭/下滑 | 草稿保存成功才退出，反馈“已保留，下次继续”；失败留在表单 |
| 编辑有变化时取消 | 收键盘后就地继续/放弃；不覆盖原任务，也不清空另一份草稿 |
| 保存失败 | 输入保留；当前列表不出现假成功数据；允许重试 |
| 快速重复点击添加 | 在途命令不可重复执行，成功后一个对象；保存任务与清草稿在一个事务内 |
| 切后台或异常退出 | 自动检查点可降低损失，但须在原生切片中验证；不承诺操作系统终止前必定保存最新键入字符 |

这里明确采用草稿并接受它的维护成本，是为了演示中断语义；不是所有短输入工具都必须持久化草稿。实现前可以用真实试用比较直接关闭确认与草稿方式，选择改变时同步更新此契约。

## 4. 完成、撤销与日期变化

点复选框提交完成，持久化成功后才移到“今日已完成”组；出现短暂撤销入口。该组可随时展开恢复任务，撤销入口消失不等于失去恢复能力。保存失败则复选框和列表位置恢复，并就近说明。

今天的完成组按完成时刻在当前时区对应的日期查询，安排日期不随完成改变。将来若要统计完成习惯，需另定义旅行换时区后的历史归属，不能先从视觉分组推断统计规则。

回前台和跨日后刷新今天；仅浏览界面变更，原安排日期不随系统日期推进。此切片没有通知调度，不能因日期已存入本地便显示“提醒已开启”。

## 5. 实现边界

| 状态/组件 | 唯一拥有者与责任 |
| --- | --- |
| 任务、草稿 | 仓储内实体；应用命令统一保存和失败回滚 |
| 今天/全部、滚动位置 | 会话状态；新建/编辑返回保留 |
| 标题、日期、焦点 | 表单临时状态；创建成功才提交为任务 |
| TaskRow | 只接收任务展示值与完成/打开事件，不直接写库 |
| TaskEditor | 当前值、提交结果、取消契约；不持有整份可写数据仓库 |
| 当前日期 | 可注入时钟；正式环境刷新，测试可冻结 |
| 恢复入口 | 读失败时暂停危险写入、原数据保留；恢复完成再进入可写列表 |

具体存储选型在原生实现阶段按数据规模、查询与未来扩展决定，不预先复制余记 JSON 全量仓储。最小不变量：ID 唯一、标题非空、完成标识与完成时间一致、任务保存与草稿清理原子化、读失败不会创建并覆盖可写空库。

## 7. 这次练习暴露了什么

填模板时必须回答的真实问题，不止“页面长什么样”：默认日期来自哪里；保存后不在当前列表怎么办；草稿从另一视图打开时是否改日期；短暂撤销消失后如何纠错；跨日刷新会不会让任务消失。这些决策已经具体写入上文，而不能只列成“注意用户体验”。

方法在设计层帮助发现了这些问题；没有运行原生 App，也没有独立对照或用户计时，因此不能据此宣布效率提升、体验达标或 Skill 的跨应用效果已验证。下一步如果用户启动待办项目，可将此稿作为候选简报，再按真实需求修正。
