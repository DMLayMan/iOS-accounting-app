# 架构与交付：把可维护性用在真实风险上

适用于小团队或个人维护的 iOS 工具。可复用的是边界和决策方式，不是把某个记账项目完整复制到日程应用。

## 1. 先交付一条完整路径

优先完成“首次打开 → 创建真实对象 → 保存 → 重新读取 → 编辑 → 取消/失败 → 恢复”，再横向铺开管理页与分析页。提前检查计划交付的设备、签名、系统版本和权限条件；环境未满足时保留真实范围，继续完成可验证部分。

对低风险布局先用线框或可交互 demo 验证层级；涉及键盘、拖动、sheet、返回、滚动和系统材质时，尽早做最小原生切片。原型与原生不长期维持两套平行产品；方向已定就把当前规范和证据迁到原生。

## 2. 划分责任，不先建框架

| 责任 | 应包含 | 不应偷偷承担 |
| --- | --- | --- |
| 页面 | 呈现、焦点、临时表单与导航 | 写文件、复制统计公式 |
| 共用组件 | 明确的输入、事件、状态呈现 | 看不见的全局副作用、隐式落盘 |
| 应用状态/用例入口 | 用户命令、成功失败、状态协调 | 多份互不一致的领域数据 |
| 领域 | 实体关系、计算、约束 | SwiftUI 焦点与页面布局 |
| 仓储 | 读写、兼容、事务/恢复边界 | 替用户决定哪个页面该关闭 |
| 系统适配 | 原生控件、权限、分享、平台 API | 另造一套主题或业务规则 |

简单应用不必每页一个 Store、一个 ViewModel。SwiftUI 无法达到某个必要交互时可以局部采用 UIKit，封装桥接生命周期和输入输出；不因追求“纯 SwiftUI”牺牲操作体验。

## 3. 复用分三层

| 层 | 适合复用 | 需要重新设计的内容 |
| --- | --- | --- |
| 平台体验基础 | 语义颜色、按钮状态、表单退出协议、输入互斥、原生桥接与销毁 | 不同应用的品牌、结构和文案 |
| 产品内共用能力 | 日期期间选择、目录管理、对象行、筛选状态、计算服务 | 业务口径不同的状态，不为外观一致强行合并 |
| 领域专属能力 | 在当前领域内部复用计算和校验 | 退款、预算、待办重复规则、日程时区语义不能相互照搬 |

真实的多个调用方开始出现重复行为时再抽取。先对照差异，把相同契约收进组件，保留业务差异在调用方或显式策略中。若出现许多布尔样式开关、按页面名判断、或入参为整个可写 Store，检查抽象边界是否错了。不要因为可能有第二款 App 就立刻发布通用 SDK。

组件说明至少包含：输入、事件、唯一状态拥有者、持久化责任、取消/失败、无障碍和生命周期。以日期组件为例，整段头部、选中态、选择面板与取消逻辑共同复用，才不会出现两个页面各长出一套时间 Tab。

## 4. 状态所有权表是最划算的架构产物

为每类状态填写“谁拥有、谁可修改、是否持久化、何时重置、返回后是否保留”。区分：

- 已保存实体与偏好；
- 跨页面共享的会话上下文；
- 页面局部筛选/排序；
- 未提交表单和草稿；
- 焦点、手势、临时动画。

共享状态应有一个权威来源，镜像只能通过统一命令更新；不同语义的上下文不必共享。一个页面动作不能无意清理另一个页面的草稿。编辑后的退出判断比较用户可编辑字段，不使用会自动变化的时间戳制造假 dirty。

## 5. 本地可靠性也是用户体验

推荐写入契约：捕获旧状态或开启事务 → 领域变更 → 校验结果 → 持久化 → 成功更新可见状态 → 关闭表单。失败恢复可用旧状态并保留输入。具体可以用数据库事务或小数据快照，不要求所有应用使用 JSON。

读取旧文件失败时，保留原字节并阻断可能覆盖它的写入；提供重试/恢复。恢复外部备份时先隔离校验、预览影响、保留当前数据或损坏原文件，再替换；保留失败就不能继续替换。生成导出文件、系统分享完成、外部目的地确实保存是不同事实。

校验覆盖本地读、写、恢复，单一维护规则。至少考虑稳定 ID、重复操作、对象引用、合法日期/值域、归档历史、版本兼容、级联影响。历史引用合法不等于允许新对象继续使用被归档实体。计算合计前先处理溢出边界，不能让“校验备份”本身崩溃。

按领域选数据类型：金额可用最小单位整数；日程要区分绝对时刻、当地日期和时区；待办要明确完成事件与重复实例。不要把记账的 CNY、Day 或退款语义写成通用基础设施。

## 6. 少依赖与低维护的边界

先评估本地能力能否完成用户价值，再增加网络依赖。为现有持久化提供小而稳定的仓储接口；schema 演进和恢复路径比提前引入复杂同步框架更有价值。

“不自建服务端”仍可能依赖平台托管服务。iCloud 同账号同步、不同账号共享、权限邀请、冲突与撤权是不同能力。未完成真实连接与冲突验收前，只展示准确的可用状态；设置开关和本地字段不能证明同步成功。新的系统 API、签名和发布规则按实施时的官方资料核实。

当新增 Widget、扩展、多进程写入或云同步时，重新审查并发边界，不能让多个写入者各自保存整份 JSON。若改异步持久化，还要防旧请求晚完成后覆盖新状态。依据设备上的保存延迟、内存和响应数据再选索引、数据库或 actor；500 条合成记录通过不能推断 50,000 条性能。

原生桥接控件要覆盖销毁、取消、后台切换和复用。计时器、display link、观察者和回调的引用关系不能只依赖 deinit；如果它们持有对象，deinit 本身可能不会发生。

## 7. Coding agent 的高效闭环

| 阶段 | 最小有用产物 | 进入下一步的依据 |
| --- | --- | --- |
| 明确需求 | 一页任务/边界/验收 | 关键语义和高影响选择清楚 |
| 设计选择 | 一条完整动线 + 必要状态 | 主要不确定性已有具体证据或已标注假设 |
| 原生切片 | 能保存与回读的最小功能 | 用户任务贯通，核心数据可验证 |
| 扩展实现 | 复用契约、风险对应测试 | 无新的状态/计算分叉 |
| 集中审查 | 当前原生截图与问题表 | 修复可观测问题并复测 |
| 交付 | 当前文档、证据、构建或 PR | 实际状态与声明一致 |

减少上下文重复读取：将已确认产品决策、当前设计、架构边界和验收入口放在稳定路径，历史方案单独标记。代理读当前基线后只深入本次影响区域。

测试从快速领域检查开始，再跑受影响原生路径；共享组件或发版前扩大到场景矩阵。UI 定位失败先判断是产品不可操作、旧测试入口、键盘遮挡、时钟、滚动命中还是运行器错误，不为“变绿”删掉正确的数据断言。

业务时钟可注入，正式环境覆盖回前台/跨日；测试为每次运行生成独立存储标识，非法标识拒绝进入个人仓储。构建产物和日志按批次固定；不要测试中改脚本、重建同目录或让另一运行改同一清单。

## 8. 度量效率但不制造数字

“极致效率”可观察为：从任务明确到可验收产物的时间、无效返工次数、重复等待成本和下一次改动成本。不要把代码行数、截图数或测试数当成生产力本身。

为一两项核心任务记录基线与改后值：首次成功步骤/时间、熟练重复任务时间、离开原上下文次数、错误恢复步骤、失败后输入保留情况。人工走查与真实用户测量分开标记；没有真实用户或埋点不编造满意度和节省比例。

每轮新增质量门槛都应对应实际风险或近期回归。已经通过且未受后续改动影响的重测试只增加成本；保持可追溯的全量加针对性复测，而不是一直重跑一切。
